这是一个非常扎实的企业级网关架构设计。结合你使用的技术栈（Apache SSHD, AWS SDK v2 Netty, 本地磁盘缓存），我为你整理了一份完整的**架构设计文档**。

这份设计旨在解决三个核心问题：**高并发下的内存保护**、**多用户流量复用**、**强一致性保障**。

-----

### 一、 总体架构设计 (High-Level Architecture)

采用 **无共享（Shared-Nothing）集群架构**。每个网关节点独立运行，节点之间不共享缓存，依靠负载均衡器（LB）分发流量。

* **接入层 (L4 LB)**：TCP 负载均衡（Nginx/AWS NLB）。将 SFTP 连接随机或按最少连接数分发到网关节点。
* **网关节点 (Gateway Node)**：
    * **前端**：Apache SSHD（处理 SFTP 协议，阻塞式/同步模型）。
    * **核心**：资源协调层（负责去重、缓存管理、一致性校验）。
    * **后端**：AWS SDK v2（基于 Netty，异步非阻塞 IO）。
    * **缓存**：本地 SSD 临时文件（利用 OS PageCache 加速）。
* **存储层 (S3)**：单一数据源。

-----

### 二、 节点内部模块设计 (Internal Component Design)

在单个 Java 进程内部，我们采用 **适配器模式（Adapter Pattern）** 将 SSHD 的同步读取桥接到 Netty 的异步下载上。

#### 1\. 模块分层图

```text
[ SFTP 客户端 (FileZilla/Script) ]
        |  (SFTP Protocol)
        v
-------------------------------------------------------
| Apache SSHD Server (Worker Threads)                 |
|   -> SftpSubsystem                                  |
|      -> S3FileSystem (虚拟文件系统)                  |
|         -> S3SeekableByteChannel (适配器/消费者)      | <--- 1. 阻塞读取 (wait)
-------------------------------------------------------
        |
        | (通过 Manager 获取/订阅)
        v
-------------------------------------------------------
| 核心资源层 (Core Resource Layer)                     |
|   -> S3BroadcasterManager (单例/Map)                |
|      -> S3Broadcaster (生产者/状态机)                 | <--- 2. 唤醒通知 (notify)
|         - 持有 TempFile (磁盘)                       |
|         - 持有 ETag/VersionId (一致性指纹)            |
-------------------------------------------------------
        |
        | (异步 IO)
        v
-------------------------------------------------------
| AWS SDK v2 (Netty Client)                           |
|   -> AsyncResponseTransformer                       |
|      -> DirectByteBuffer -> FileChannel.write()     |
-------------------------------------------------------
        |
        v
   [ AWS S3 ]
```

#### 2\. 核心组件定义

| 组件名 | 角色 | 职责 | 关键特性 |
| :--- | :--- | :--- | :--- |
| **S3FileSystemProvider** | 工厂入口 | 拦截文件打开操作；向 Manager 申请资源。 | 实现 Java NIO SPI 接口。 |
| **S3BroadcasterManager** | 注册中心 | 维护 `Map<FileKey, Broadcaster>`；实现“去重”逻辑。 | 线程安全，管理 Broadcaster 生命周期。 |
| **S3Broadcaster** | **生产者** | 1. 维护唯一的 S3 连接；<br>2. 将数据写入本地临时文件；<br>3. 处理 S3 异常并熔断。 | **一写多读**；持有 `FileChannel` (Write)。 |
| **S3SeekableByteChannel** | **消费者** | 1. 适配 SSHD 的 `read()` 接口；<br>2. 挂起线程等待数据；<br>3. 从本地文件读取数据。 | 每个客户端一个实例；持有 `FileChannel` (Read)。 |

### 三、 核心工作流程 (Workflows)

#### 1\. 建立连接与下载流程 (The "Join" Flow)

当客户端请求读取 `/bucket/video.mp4` 时：

1.  **Check (元数据校验)**：
    * `Manager` 发起 `HEAD` 请求获取 S3 的 `ETag: v1` 和 `Content-Length`。
2.  **Lookup (查找或创建)**：
    * `Manager` 检查内存中是否有 `Key="video.mp4::v1"` 的 `Broadcaster`。
    * **场景 A (第一个用户)**：不存在。创建新的 `Broadcaster`，启动 S3 异步下载任务（写入 `/tmp/uuid.part`）。
    * **场景 B (后续用户)**：已存在。直接返回该对象，引用计数 +1。
3.  **Bind (绑定)**：
    * 创建 `S3SeekableByteChannel`，绑定到该 `Broadcaster`。
4.  **Read (流式读取)**：
    * 客户端请求读取 offset 0-32KB。
    * `Channel` 检查 `Broadcaster` 进度。
        * 如果有数据：直接从磁盘读。
        * 如果没数据：`lock.wait()` 阻塞当前 SSHD 线程。
    * 后台 Netty 线程下载数据写入磁盘 -\> 更新进度 -\> `lock.notifyAll()`。
    * SSHD 线程被唤醒，读取数据返回。

#### 2\. 强一致性保障流程 (The "Consistency" Flow)

如何处理下载过程中 S3 文件被覆盖的情况？

1.  **锁定指纹**：`Broadcaster` 初始化时记录 `ETag: v1`。
2.  **带锁请求**：`Broadcaster` 向 S3 请求 Range 数据时，HTTP 头必须包含 `If-Match: v1`。
3.  **异常熔断**：
    * S3 返回 **412 Precondition Failed**。
    * `Broadcaster` 捕获异常，设置状态为 `ABORTED`。
    * 唤醒所有正在 wait 的 `S3SeekableByteChannel`。
    * Channel 醒来发现状态是 ABORTED，抛出 `IOException`。
    * 客户端收到错误，连接断开。**（坚决不传脏数据）**

#### 3\. 资源清理流程 (The "Cleanup" Flow)

1.  **断开连接**：客户端断开 SFTP 连接，SSHD 调用 `channel.close()`。
2.  **减少引用**：`Broadcaster.release()` 被调用，引用计数 -1。
3.  **销毁判断**：
    * 如果引用计数 == 0：
        * 从 `Manager` 的 Map 中移除自己。
        * 取消正在进行的 S3 Netty 任务。
        * **删除本地临时文件**。

### 四、 关键技术决策 (Design Decisions)

#### 1\. 为什么选“本地磁盘缓存”而不是“纯内存”？

* **内存安全**：如果 100 个用户下载 100 个大文件，纯内存方案容易 Heap OOM 或 Direct Memory 耗尽。磁盘缓存将压力转嫁给存储，Java 堆内存占用极低。
* **复用性**：磁盘文件天然支持随机读（Random Access）。如果 User A 下载了前 50%，User B 进来要读 offset 0，直接读文件即可，无需内存中维护复杂的环形缓冲区。
* **性能**：Linux 的 **PageCache** 会自动缓存热点文件的内容到空闲内存中。写入文件再立刻读取，实际上往往是在内存中完成的，速度极快（Zero-Copy 效果）。

#### 2\. 为什么需要“阻塞适配器”？

* **框架限制**：Apache SSHD 的 `SftpSubsystem` 是基于 `InputStream/SeekableByteChannel` 的同步 API 设计的。
* **背压 (Backpressure)**：通过 `wait/notify` 机制，天然实现了背压。如果 S3 下载慢，SSHD 线程就会阻塞等待，不会导致内存积压。

### 五、 总结与下一步

**这套架构的优点：**

1.  **高可用**：节点无状态（缓存仅在连接存活期有效），LB 可随意调度。
2.  **低内存**：利用磁盘承载数据，JVM 仅维护控制逻辑。
3.  **强一致**：利用 ETag 锁死版本，杜绝脏读。
4.  **高吞吐**：N 个用户下载同一文件，S3 只有 1 份流量。
